1. Purpose

Replace spreadsheet-based treasury facility tracking with a system that:

  • Maintains master data (banks, facilities/limits, products, rate rules, fee rules)
  • Captures instrument transactions and their lifecycle events (issuance, partial drawdown, collection, commitment, repayment, amendment, cancellation)
  • Computes utilisation, outstanding, interest, fees, and maturity using configurable formulas
  • Produces operational and management reports (limit utilisation, bank-wise position, maturity ladder, forecasts)

The design must be generic: new banks, facilities, and instrument types can be added via configuration without rewriting core logic.

2. Scope

2.1 In scope

  • Master data administration
  • Transaction capture for multiple instrument types (initially LC, LC Bill/Collection, TR, BG/SBLC; extensible)
  • Partial movements (partial collection, partial repayment, partial commitment utilisation)
  • Configurable interest and fee calculation rules
  • Limit / sub-limit utilisation against sanctioned facilities
  • Standard reports and dashboards listed in §7
  • Audit trail of who changed what and when

2.2 Out of scope (initial release unless agreed)

  • Core banking / payment initiation (SWIFT send)
  • Full accounting GL posting (may export journals later)
  • Customer-facing portal
  • Hedging / derivatives valuation engines
  • Document management for full LC document sets (store references/links only)

2.3 Design principles

  1. Config over hard-code — banks, instruments, limit structures, rate formulas are data.
  2. Event-sourced balances — outstanding is derived from events (issue, draw, collect, repay), not a single overwritten balance cell.
  3. One source of truth — reports never require pasted copies of the same deal.
  4. Typed vs computed — screens clearly separate user-entered fields from system-calculated fields.

3. Core concepts (domain model)

ConceptMeaningExamples
Bank Financial counterparty that grants facilities and books instruments Any commercial bank / FI
Facility Sanctioned limit line (optionally with sub-limits by product, geography, or use) Working capital USD 260m; Zambian sub-limit 85m
Instrument type Configurable product category with its own lifecycle and calculation profile LC, LC Bill, TR, BG, SBLC, TT, Term Loan, FD, ICD, …
Instrument (deal) A single contract/reference under a bank + facility + instrument type One LC number; one BG number; one TR reference
Lifecycle event Atomic movement that changes commitment or outstanding Issue, amend, bill present, partial collect, draw TR, partial repay, cancel
Calculation rule Named formula for interest or fees, with parameters SOFR + markup / 360; Fixed % p.a. × quarters; flat fee + VAT%
Utilisation snapshot Point-in-time outstanding by facility / bank / instrument type / status Month-end MoM history; as-of report
Relationship (simplified): Bank 1—N Facility 1—N Instrument 1—N Lifecycle Event. Instrument Type defines allowed events and default calculation rules. Facility defines sanctioned amount; utilisation = sum of Live outstanding events/instruments booked to that facility.

5. Functional requirements

5.1 Master data

IDRequirementPriority
FR-M01 System shall allow create/update/deactivate of Banks (code, name, country, SWIFT, status). Must
FR-M02 System shall allow Facilities with sanctioned amount, currency, bank, start/end date, and optional sub-limits (by product, region, or custom dimension). Must
FR-M03 System shall allow configuration of Instrument Types (code, name, whether they consume NFB/FB limit, allowed event types, default status rules). Must
FR-M04 System shall allow configuration of Calculation Rules for interest and fees (see §5.4), attachable at instrument type, facility, bank, or deal override level. Must
FR-M05 System shall support reference lists: currencies, commodities/products, entities/companies, status codes, charge types. Must
FR-M06 Deactivating a master must not delete historical deals; new bookings to inactive masters shall be blocked. Must

5.2 Instruments & lifecycle events

IDRequirementPriority
FR-T01 User shall create an Instrument by selecting Bank, Facility (or sub-limit), Instrument Type, and entering type-specific attributes (dates, counterparties, reference numbers, amounts, tenor, etc.). Must
FR-T02 System shall support multiple instrument types without separate hard-coded applications. Screens may show type-specific field groups driven by configuration. Must
FR-T03 User shall post Lifecycle Events against an instrument: e.g. Issue / Amend / Bill Present / Partial Collection / Full Collection / Draw / Partial Repayment / Full Repayment / Commitment set / Cancel / Expire. Must
FR-T04 Each event shall record: event type, effective date, amount (and currency), optional linked reference (e.g. bill ref → LC), narrative, and who entered it. Must
FR-T05 Partial movements shall be first-class: outstanding = sum(signed event amounts) per configured balance type (Commitment, Utilised, Outstanding Principal, etc.). Over-repayment shall be prevented or flagged per rule. Must
FR-T06 Instruments may be linked (e.g. LC Bill → parent LC; TR → Bill Ref / LC). Links are used for enrichment and utilisation roll-up, not duplicate data entry of shared attributes where avoidable. Must
FR-T07 System shall compute Status (e.g. Live / Expired / Cancelled / Settled) from rules: due/claim date vs as-of date and/or outstanding ≠ 0. Rules configurable per instrument type. Must
FR-T08 Amendments to master deal fields shall be versioned or audited; financial amount changes should normally be via events, not silent overwrite. Should

5.3 Limits & utilisation

IDRequirementPriority
FR-L01 For any as-of date, system shall calculate Utilised and Available per Facility / Sub-limit = Sanctioned − sum(Live outstanding of instruments that consume that limit). Must
FR-L02 Instrument types shall declare whether they consume facility limit and which balance (e.g. LC O/s incl. tolerance, TR O/s, BG amount). Must
FR-L03 System shall support warning or hard-block when a new event would breach sanctioned limit (configurable per facility). Should
FR-L04 Utilisation shall be sliceable by Bank, Facility, Instrument Type, Commodity/Product, Status, Entity. Must

5.4 Interest & fee calculation (configurable)

IDRequirementPriority
FR-C01 System shall support multiple interest calculation methods, selectable per deal or type, including at least:
  • Base rate + margin, day count 360 or 365/Actual
  • Fixed rate × principal × days / day-count basis
  • Quarterly (or N-period) commission on amount × rate × periods
  • Flat fee / manual amount (user-entered) with optional VAT%
 Must
FR-C02 Day-count and accrual period (from/to dates) shall be explicit on the calculation; partial periods from partial repayments shall accrue only on remaining principal for the relevant days. Must
FR-C03 User may enter actual bank-debited charges; system computes expected charges and shows Variance. Must
FR-C04 New calculation formulas shall be addable by configuration (parameters + formula template), not only by code change, for common treasury patterns. Should
FR-C05 FX conversion for reporting (e.g. to USD or INR) shall use deal FX, daily rate table, or manual rate — selectable and auditable. Should

5.5 Maturity & forecasting

IDRequirementPriority
FR-F01 System shall produce a maturity ladder of Live instruments by maturity/due/claim date, bank, facility, type, amount. Must
FR-F02 System shall support a limit forecast view (e.g. weekly buckets) combining known maturities / expected utilisations with optional manual pipeline amounts. Should
FR-F03 System shall store period-end snapshots for month-on-month history without requiring users to paste data. Should

5.6 Audit & controls

IDRequirementPriority
FR-A01All create/update/delete of masters, instruments, and events shall be audit-logged (user, timestamp, before/after).Must
FR-A02Role-based access: Operator / Lead / Admin / Viewer as in §4.Must
FR-A03As-of date parameter on all financial reports (default = today).Must

9. Delivery phasing (recommended)

PhaseDeliverables
Phase 1 — Core Masters (Bank, Facility, Instrument Type, basic Calc Rules) · Instruments + Events for LC, LC Bill, TR, BG · Limit Utilisation · Bank-wise · Maturity Ladder · Audit & roles
Phase 2 — Pricing & forecast Full interest/fee engine + variance · Limit Forecast · Executive Dash · Period snapshots
Phase 3 — Extended instruments Additional types as needed (e.g. TT/Open Credit, Term Loan, FD, ICD, Export) using same framework · Liquidity board if required
This matches the earlier product understanding: (1) masters → (2) instrument inputs (starting with four types) → (3) reports, while keeping the model open for more banks and instruments later.
