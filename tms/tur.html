1. Purpose

Replace the current multi-Excel treasury estate with one platform that:

  • Maintains shared master data (banks, bank accounts, facilities/limits, products, rate/fee rules, cash categories)
  • Captures instruments and lifecycle events (LC, LC Bill, TR, BG, … — extensible)
  • Imports / records bank statements and supports matching to forecast lines (and optionally invoices)
  • Maintains cash forecast with explicit Projected vs Actual and variance
  • Computes utilisation, outstanding, interest/fees, maturity, free cash
  • Produces operational and management reports without re-keying the same deal into a second workbook
Excel today vs app tomorrow: Facility utilisation and Weekly Cashflow are only loosely coupled (manual paste / shared reference numbers). The application must store instruments, cash movements, and statements in one schema so booking an LC due date can seed a projected cash line, and a matched bank credit can mark Actual — without users maintaining parallel Utilisation / Lines copies.

2. Scope

2.1 In scope

  • Master data administration (including bank accounts and cash-line categories)
  • Instrument capture + lifecycle events (partial draw / collect / repay / commit)
  • Configurable interest and fee calculation rules
  • Limit / sub-limit utilisation
  • Cash forecast (by week and/or by bank account)
  • Bank statement import and classification
  • Matching forecast ↔ statement (↔ optional invoice/document)
  • Projected vs Actual with variance explanations
  • Free-cash / earmark view driven from live data
  • Standard reports (§7) and audit trail

2.2 Out of scope (initial unless agreed)

  • Core banking payment initiation (SWIFT send)
  • Full GL posting (export journals later)
  • Customer portal; derivatives valuation; full LC document DMS

2.3 Design principles

  1. One schema, many views — facility screens and cash screens read/write the same entities.
  2. Config over hard-code — banks, accounts, instruments, match rules, formulas are data.
  3. Event-sourced balances — outstanding and cash Actuals come from events/matches, not overwritten cells.
  4. No duplicate masters — LC / TR / BG exist once; cash forecast lines reference them.
  5. Typed vs computed — UI separates user input from system-calculated fields.

3b. Unified schema (anti-duplication)

Today’s Excels force users to maintain facility deals in one file and re-paste similar lines into Weekly Cashflow (Utilisation / Lines) plus re-type Actuals from statements into CF. The app shall use a common schema so each fact is entered once.

IDRequirementPriority
FR-U01 Instruments, facilities, banks, and accounts shall be stored once and reusable by limit screens and cash screens. Must
FR-U02 Creating/updating a lifecycle event that implies cash (due date, repay, collection) shall be able to create or refresh ExpectedCashMovement(s) without re-keying in a separate cash workbook. Must
FR-U03 Limit utilisation and cash earmarks shall calculate from the same Live outstanding / open movements — not from a pasted “Utilisation” sheet. Must
FR-U04 Users may still add manual forecast lines (trade receivables, ad-hoc) that are not tied to an instrument; these use the same ExpectedCashMovement entity. Must
FR-U05 UI shall warn when the same bank reference or instrument reference is linked twice in conflicting matches. Should

IDRequirementPriority
FR-CF01 System shall maintain a cash forecast of ExpectedCashMovements with: direction (in/out), amount, CCY, value date, bank account (optional), category/desk, counterparty, link to instrument/event (optional), Projected amount, Actual amount, status. Must

5.7 Matching & Forecast vs Actual

IDRequirementPriority
FR-MT01 User (or auto-suggest) can match one or more StatementLines to one or more ExpectedCashMovements (1:1, 1:N, N:1, partial amount). Must
FR-MT02 On match confirm: set/increase Actual on the movement; statement line status → matched/partial; record match audit. Must
FR-MT03 Variance = Actual − Projected (sign rules by direction); user may enter variance reason. Must
FR-MT04 Unmatched statement lines and unmatched past-due Projected movements shall be listable as work queues. Must
FR-MT05 Auto-suggest matches using: amount±tolerance, date±window, bank reference, counterparty name similarity, linked instrument ref — configurable rules; user confirms. Should
FR-MT06 Optional third leg: link match to an invoice / document reference (supports BIM-style invoice ↔ bank ↔ cash recon). Should
FR-MT07 Unmatch / rematch allowed with audit; Actual rolled back accordingly. Must
FR-MT08 Forecast grid shall show Projected and Actual side-by-side for each period (parity with Weekly CF Actual|Projected columns), sourced from movements — not a second pasted grid. Must

9. Delivery phasing (recommended)

PhaseDeliverables
Phase 1 — Facility core Masters (Bank, Account, Facility, Instrument Type, basic Calc Rules) · Instruments + Events (LC, LC Bill, TR, BG) · Limit Utilisation · Bank-wise · Maturity · Audit/roles · Expected cash auto-create from events (foundation)
Phase 2 — Cash & matching Statement import · classification · Matching workspace · Forecast week + account views (P vs A) · Free cash · unmatched queues · replace Excel dual-maintenance for util/cash
Phase 3 — Enrich Full interest/fee + charge variance · Limit Forecast · Dash · Snapshots · Auto-match suggestions · Document three-way recon · extended instrument types (TT, TL, FD, …)
Product shape: (1) shared masters → (2) instruments + cash/statements → (3) matching & reports, with one schema so facility and cash never diverge.
